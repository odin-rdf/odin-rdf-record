# The pure encoding layer: tag 0x07 and the base-direction tag, with independent golden vectors

## Parent Initiative

[[RECORD-I-0004]]

## Objective

Build both new term encodings in the pure layer — `term_encode` and
`term_decode` in `record/term.odin` — and prove the bytes against vectors
computed independently of the Odin implementation, the way
`RECORD-T-0001` proved the record encodings.

Nothing above this layer changes in this task. The intern still refuses,
`apply` still returns `.Unsupported_Term`, and no log gains a new byte.
This is the layer the document describes, tested against the document.

## Acceptance Criteria

- [x] **Tag `0x07` encodes and decodes**, in the layout
      `architecture.md` §11.3 specified: `0x07 | sID | pID | oID`, three
      `u64`s, 25 bytes. `u64` on the wire because the log stays 64-bit
      (api.md §3.5), matching how `0x05` carries a `u64` datatype id and
      `0x06` a `u64` namespace id.
- [x] **The base-direction tag encodes and decodes**, under the tag and
      layout `RECORD-T-0021` chose. `rdf.Literal` already carries
      `direction` as an enum, so the data model needs nothing.
- [x] **Tag `0x08`'s three injectivity refusals**, from
      [[RECORD-A-0007]]'s 2026-08-24 amendment and *not in this task as
      filed*: `dir` validated against `{LTR, RTL}` (`rdf.Direction` has
      three values, so `0x03`..`0xFF` are not directions); `dir` never
      `.None` under `0x08` (else `"x"@en` encodes two ways, which is
      §3.2's language-tag defect exactly); `langlen` never zero. All
      three **decoder-side** — injectivity is the format's property, and
      the decoder is what a third party's log meets.
- [x] **Both directions are total and strict.** An unknown tag, a
      truncated payload, or a reference the resolver cannot answer is
      **not ok** — never a guess. That is `term_decode`'s standing
      contract and the reason an unknown record kind halts.
- [x] **Recursion works in the encoder**, including a triple term whose
      component is itself a triple term. The consumer's corpus contains
      one — `../odin-rdf-sparql/tests/w3c/sparql12-eval-triple-terms/construct-3.ttl`
      carries `<< _:reifier2 rdf:reifies <<( :a :b :c )>> >>` — so this is
      exercised in practice and not merely permitted. odin-rdf-parser's
      `rdf12-turtle-eval` and `rdf12-trig-eval` suites, at
      `../odin-rdf-parser/tests/w3c/`, are the fixture source from
      RECORD-T-0023 onward and need no vendoring.
- [x] **Golden vectors computed independently** — by hand or by a short
      script written from `architecture.md` §3.2 and §11.3 alone, not by
      running the Odin encoder and recording what it produced. That
      distinction is the whole value of `RECORD-T-0001`'s method: a
      golden vector generated by the implementation proves only that the
      implementation is deterministic.
- [x] **The injectivity property tested**, not just argued: no term of any
      other kind encodes to the bytes a triple term does, and two
      distinct triple terms encode distinctly. Add the converse, which is
      the half `RECORD-T-0021`'s re-check found sharper: **one term never
      encodes two ways** — no `0x08` byte string decodes to a term `0x04`
      also encodes, and a triple term whose component is an inlineable
      literal encodes with the *inline* id and no other.
- [x] **`term_inline` is untouched and proven untouched.** A triple term
      is not inlineable — three ids do not fit in 28 bits — and
      `RECORD-A-0001` froze the inline predicate at first write. A test
      that `term_inline` refuses a triple term and a base-direction
      literal keeps that frozen boundary visible.
- [x] **The format version moved or not moved per `RECORD-T-0021`**, with
      the writer, the header check (`encode.odin:243`) and the tests
      agreeing.
- [x] `make test` and `make check` green.

## Implementation Notes

### Technical Approach

**Watch the scratch buffers in the recursive encoder.** `term_encode`'s
`fit` writes into a caller-provided buffer when the encoding fits and
allocates when it does not; a recursive encoder needs each level's bytes
to outlive the level above it long enough to be copied. This is the most
likely source of a subtle bug in this task and it will not show as a
compile error.

**The base-direction lowercase rule.** `0x04` lowercases the language tag
on encode (`enc[2+i] = c + 32 if c >= 'A' && c <= 'Z' else c`) — the
canonical encoding's rule, and the reason the consumer's engine sees
`@en-nz` where a document said `@en-NZ`. Whatever tag base direction
gets, it must apply the same fold to the language half, or two encodings
of the same term exist and injectivity is gone.

### Dependencies

Blocked by RECORD-T-0021 — the decode seam, the ownership rule and the
tag choice are all inputs here.

### Risk Considerations

**A golden vector that was generated rather than derived is the failure
mode this task most needs to avoid**, because it passes. If deriving a
25-byte encoding by hand feels like ceremony, note that
`RECORD-T-0001`'s independent Python script is the reason this store can
claim a third party could verify it from the specification alone — and
`RECORD-T-0006` found that writing the independent verifier surfaced no
documentation bug, which is what the method was for.

**Do not let the decoder's recursion depth become unbounded.** A
malformed or hostile log could in principle encode deeply nested triple
terms. Since a component id is always *lower* than the term referencing
it (ids are assigned in first-appearance order), depth is bounded by the
dictionary — but that is a property to check on the replay path
(`RECORD-T-0023`), not to assume here.

## Status Updates

### 2026-08-24 — both tags land; `make test` and `make check` green

The pure layer, built to [[RECORD-A-0007]] and [[RECORD-A-0008]]. All ten
criteria met, including the two the design gate added.

**The encodings.** `TERM_TAG_TRIPLE` (`0x07`) carries three on-disk
component ids, `TERM_TRIPLE_PAYLOAD` bytes, checked **exactly** on
decode — a tolerated tail would be a second encoding of one term.
`TERM_TAG_DIR_LANG` (`0x08`) is `tag | langlen | dir | lang | lexical`
with `0x04`'s lowercase fold on the language half. Both directions are
strict; both refuse rather than guess.

**The seams.** `term_decode` gained `resolve_term: Resolve_Term = nil`
and `term_encode` gained `resolve_component: Resolve_Term_ID = nil`,
each defaulting to the refusal the codec had before. `Resolve_Term`
takes an allocator and its answer is owned, which is what makes a
decoded triple term wholly owned end to end.

**Golden vectors derived, not generated.** `tests/verify/term_vectors.py`
— new, ~120 lines of stdlib — computes them from `architecture.md` §3.2
and §11.3 and [[RECORD-A-0007]] alone, every constant citing its section,
with the three injectivity refusals asserted rather than encoded around.
It is committed, which the term-side vectors of `RECORD-T-0001` were not:
"computed independently in Python" was a claim in a comment, and now the
derivation is auditable. The Odin encoder reproduced all seven vectors
first try.

### Four things the task as filed did not anticipate

- **Base-direction literals reached the intern in this task, not the
  next.** They need no recursion, so `intern_term` accepts one the moment
  `term_encode` has a tag for it — and therefore so does `apply`. The
  task's "the intern still refuses, `apply` still returns
  `.Unsupported_Term`" holds for **triple terms only**. Gating the other
  half artificially would have been make-work; `RECORD-T-0023` inherits a
  smaller job. `test_ingest_triple_term_refused_at_apply` is untouched and
  still passes, which is the right signal: it is about a triple term.
- **`rdf.destroy_term` is the correct free, not `rdf.destroy_triple`.**
  [[RECORD-A-0008]] said the latter; for a `^rdf.Triple`, `destroy_term`
  deep frees every component *and then the node*
  (`../odin-rdf-parser/rdf/clone.odin:89`), where `destroy_triple` takes a
  `Triple` by value and leaves the node behind. The ADR and the doc
  comment are corrected. The hazard the decision turns on is unchanged —
  both reach every component string.
- **An inlined component must be cloned to be owned.** `inline_term`
  materializes a literal whose `datatype` is a *static* IRI constant, so
  handing it back unowned would have `destroy_term` free a constant. The
  test resolver clones; `RECORD-T-0024`'s real one has the same
  obligation, and the doc comment on `Resolve_Term` states it.
- **`Term_Error` gained `Unknown_Component`** — `Unknown_Datatype`'s twin
  one tag over, for a component the resolver cannot name. The intern never
  returns either, because it defines what it lacks.

### The version bump's blast radius, measured rather than predicted

`FORMAT_VERSION :: 2`. Four places assumed version 2 meant *the future*
and had to move to `FORMAT_VERSION + 1`: `test_header_golden_and_round_trip`'s
wrong-version case, `open_test`'s future-format header, and the fault
corpus's `future-version-header` mutation. `GOLDEN_HEADER` was recomputed
— independently, from `log.md` §3's layout using the Python verifier's own
CRC-32C, not by running `header_encode` — and only two fields moved: the
version and the checksum over it.

`tests/verify/rdflog_verify.py` took the one-constant change
`RECORD-T-0021` predicted, with a comment stating what did *not* change
and why. **Both verifiers still agree over the 29-case fault corpus**:
`make test` is green end to end, `tests/proof` included, which is the
claim this bump most risked.

### Untouched, and proven so

`term_inline` refuses both new kinds by test — three ids do not fit in 28
bits and `RECORD-A-0001` stays frozen. The term index, the permutations,
the fact table, `Filter`, visibility and the epoch table are unchanged;
`RECORD-T-0025` asserts that list as a whole.
