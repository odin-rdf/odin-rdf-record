# The pure encoding layer: tag 0x07 and the base-direction tag, with independent golden vectors

## Parent Initiative

[[RECORD-I-0004]]

## Objective

Build both new term encodings in the pure layer — `term_encode` and
`term_decode` in `record/term.odin` — and prove the bytes against vectors
computed independently of the Odin implementation, the way
`RECORD-T-0001` proved the record encodings.

Nothing above this layer changes in this task. The intern still refuses,
`apply` still returns `.Unsupported_Term`, and no log gains a new byte.
This is the layer the document describes, tested against the document.

## Acceptance Criteria

- [ ] **Tag `0x07` encodes and decodes**, in the layout
      `architecture.md` §11.3 specified: `0x07 | sID | pID | oID`, three
      `u64`s, 25 bytes. `u64` on the wire because the log stays 64-bit
      (api.md §3.5), matching how `0x05` carries a `u64` datatype id and
      `0x06` a `u64` namespace id.
- [ ] **The base-direction tag encodes and decodes**, under the tag and
      layout `RECORD-T-0021` chose. `rdf.Literal` already carries
      `direction` as an enum, so the data model needs nothing.
- [ ] **Tag `0x08`'s three injectivity refusals**, from
      [[RECORD-A-0007]]'s 2026-08-24 amendment and *not in this task as
      filed*: `dir` validated against `{LTR, RTL}` (`rdf.Direction` has
      three values, so `0x03`..`0xFF` are not directions); `dir` never
      `.None` under `0x08` (else `"x"@en` encodes two ways, which is
      §3.2's language-tag defect exactly); `langlen` never zero. All
      three **decoder-side** — injectivity is the format's property, and
      the decoder is what a third party's log meets.
- [ ] **Both directions are total and strict.** An unknown tag, a
      truncated payload, or a reference the resolver cannot answer is
      **not ok** — never a guess. That is `term_decode`'s standing
      contract and the reason an unknown record kind halts.
- [ ] **Recursion works in the encoder**, including a triple term whose
      component is itself a triple term. The consumer's corpus contains
      one — `../odin-rdf-sparql/tests/w3c/sparql12-eval-triple-terms/construct-3.ttl`
      carries `<< _:reifier2 rdf:reifies <<( :a :b :c )>> >>` — so this is
      exercised in practice and not merely permitted. odin-rdf-parser's
      `rdf12-turtle-eval` and `rdf12-trig-eval` suites, at
      `../odin-rdf-parser/tests/w3c/`, are the fixture source from
      RECORD-T-0023 onward and need no vendoring.
- [ ] **Golden vectors computed independently** — by hand or by a short
      script written from `architecture.md` §3.2 and §11.3 alone, not by
      running the Odin encoder and recording what it produced. That
      distinction is the whole value of `RECORD-T-0001`'s method: a
      golden vector generated by the implementation proves only that the
      implementation is deterministic.
- [ ] **The injectivity property tested**, not just argued: no term of any
      other kind encodes to the bytes a triple term does, and two
      distinct triple terms encode distinctly. Add the converse, which is
      the half `RECORD-T-0021`'s re-check found sharper: **one term never
      encodes two ways** — no `0x08` byte string decodes to a term `0x04`
      also encodes, and a triple term whose component is an inlineable
      literal encodes with the *inline* id and no other.
- [ ] **`term_inline` is untouched and proven untouched.** A triple term
      is not inlineable — three ids do not fit in 28 bits — and
      `RECORD-A-0001` froze the inline predicate at first write. A test
      that `term_inline` refuses a triple term and a base-direction
      literal keeps that frozen boundary visible.
- [ ] **The format version moved or not moved per `RECORD-T-0021`**, with
      the writer, the header check (`encode.odin:243`) and the tests
      agreeing.
- [ ] `make test` and `make check` green.

## Implementation Notes

### Technical Approach

**Watch the scratch buffers in the recursive encoder.** `term_encode`'s
`fit` writes into a caller-provided buffer when the encoding fits and
allocates when it does not; a recursive encoder needs each level's bytes
to outlive the level above it long enough to be copied. This is the most
likely source of a subtle bug in this task and it will not show as a
compile error.

**The base-direction lowercase rule.** `0x04` lowercases the language tag
on encode (`enc[2+i] = c + 32 if c >= 'A' && c <= 'Z' else c`) — the
canonical encoding's rule, and the reason the consumer's engine sees
`@en-nz` where a document said `@en-NZ`. Whatever tag base direction
gets, it must apply the same fold to the language half, or two encodings
of the same term exist and injectivity is gone.

### Dependencies

Blocked by RECORD-T-0021 — the decode seam, the ownership rule and the
tag choice are all inputs here.

### Risk Considerations

**A golden vector that was generated rather than derived is the failure
mode this task most needs to avoid**, because it passes. If deriving a
25-byte encoding by hand feels like ceremony, note that
`RECORD-T-0001`'s independent Python script is the reason this store can
claim a third party could verify it from the specification alone — and
`RECORD-T-0006` found that writing the independent verifier surfaced no
documentation bug, which is what the method was for.

**Do not let the decoder's recursion depth become unbounded.** A
malformed or hostile log could in principle encode deeply nested triple
terms. Since a component id is always *lower* than the term referencing
it (ids are assigned in first-appearance order), depth is bounded by the
dictionary — but that is a property to check on the replay path
(`RECORD-T-0023`), not to assume here.
